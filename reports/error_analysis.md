# Bad Case 分析报告

## 一、评测概览

评测集：50 条标注数据，覆盖 6 类场景（单工具调用 / 拒调用 / 参数追问 / 干扰请求 / 语义干扰 / 口语表达）

| 指标 | Base | SFT | DPO |
|------|------|-----|-----|
| JSON 合法 | 41/50 (82%) | **50/50 (100%)** | 49/50 (98%) |
| 工具选择正确 | — | 34/50 (68%) | 35/50 (70%) |
| 完全正确 | 14/50 (28%) | **27/50 (54%)** | 21/50 (42%) |
| Bad Cases 总数 | 36 | **23** | 29 |

**核心发现**：SFT 是最佳模型（23 个 bad cases），DPO 在部分维度有改进但在其他维度有回退。

## 二、错误类型演变分析

### 2.1 JSON 格式错误

| 模型 | 数量 | 趋势 |
|------|------|------|
| Base | 9 | — |
| SFT | **0** | ✅ 完全消除 |
| DPO | 2 | ⚠️ 重新出现 |

**分析**：SFT 训练数据全部使用 `json.dumps()` 生成标准 JSON，教会了模型输出合法 JSON。DPO 重新引入 2 例格式错误，可能是偏好训练时某些 rejected 样例（如缺少引号的 JSON）干扰了模型。

**样例**：
```
输入: "帮我预约 2026-07-01 上午 10:00 的技术方案讨论"
Base: JSON 正常但缺参数
SFT:  ✅ 完整合法 JSON
DPO:  ⚠️ arguments 偶尔输出为字符串类型
```

### 2.2 该拒未拒（应输出 none 却调用工具）

| 模型 | 数量 | 趋势 |
|------|------|------|
| Base | 14 | — |
| SFT | 11 | ⬇ 改进 21% |
| DPO | **7** | ⬇ 改进 50% |

**分析**：这是 DPO 最显著的正面效果！DPO 数据中"不该调却调工具"的 rejected 样例起了作用。

**样例**：
```
输入: "今天天气怎么样"
Base:  ❌ 调用了 search_docs
SFT:   ❌ 调用了 calculator（编造了温度计算表达式）
DPO:   ⚠️ 输出了 none + need_clarification（最好的方向，但仍有多余追问）
```

### 2.3 不必要的追问（过度使用 need_clarification）

| 模型 | 数量 | 趋势 |
|------|------|------|
| Base | 0 | — |
| SFT | 5 | ⚠️ 新引入 |
| DPO | **10** | ❌ 加剧 |

**分析**：这是 SFT/DPO 训练的副作用。SFT 数据中包含 40 条"参数缺失追问"样本，模型学会了 `need_clarification` 机制，但**过度泛化**了——对简单的问候（"你好"）、闲聊（"讲个笑话"）也追问。

**样例**：
```
输入: "你好"
SFT:   {"tool": "none", "need_clarification": true, "question": "请问您是客户还是客服？"}
DPO:   {"tool": "none", "need_clarification": true, "question": "请问你是谁？。"}
期望:  {"tool": "none", "arguments": {}}
```

**改进方向**：增加"问候/闲聊 + `{"tool": "none"}` 无追问"的 DPO 偏好对。

### 2.4 该追问却直接调用工具（参数缺失时编造）

| 模型 | 数量 | 趋势 |
|------|------|------|
| Base | 5 | — |
| SFT | 5 | ➡ 未改善 |
| DPO | 7 | ⚠️ 略恶化 |

**分析**：这是横跨三模型的**最难问题**。模型倾向于"做点什么"而非"说我不知道"。这是小模型的固有倾向——参数缺失场景在训练数据中占比太小（仅 7%）。

**样例**：
```
输入: "帮我预约个会议"（缺日期/时间/主题）
Base:  ❌ 编造了 2023-04-15 的会议
SFT:   ❌ 编造了 2026-07-18 的会议
DPO:   ❌ 改调 send_email
```

### 2.5 参数值错误（提取了近似但不准确的参数）

| 模型 | 数量 | 趋势 |
|------|------|------|
| Base | 5 | — |
| SFT | **2** | ⬇ 改进 60% |
| DPO | 3 | ➡ 基本持平 |

**分析**：SFT 大幅改善了参数提取精度。DPO 的轻微回退可能源于偏好数据中"缺少参数"的 rejected 样例让模型在参数提取上更保守。

## 四、改进建议

### 优先级 P0（当前最严重）
1. **减少"不必要的追问"**
   - 增加"DONT over-clarify"类型 DPO 数据
   - 在 DPO rejected 中增加"对简单问候追问"的错误样例

2. **修复 DPO JSON 格式回退**
   - 检查 DPO 训练数据中 rejected JSON 格式是否合理
   - 增加 JSON 格式强化的 DPO 对

### 优先级 P1
3. **攻克"参数缺失追问"**
   - 增加 clarification 型 SFT 数据至 15%+
   - 考虑加入多轮对话训练

### 优先级 P2
4. **修复"语义干扰"（日期询问 → 错调 query_order）**
   - 增加"日期/时间询问"的拒调用训练数据

---

## 五、结论

1. **SFT 是当前最佳模型**：54% 完全正确率，100% JSON 合法率
2. **DPO 有得有失**：改善了"该拒未拒"（-36%），但引入了"不必要的追问"（+100%）和 JSON 回退
3. **参数追问场景是三模型共同的盲区**：需要更多针对性数据
4. **小模型（0.5B）的语义理解上限明显**：日期询问、模糊意图等需要更强的基础能力
